Feature-Sliced Design: как это выглядит на плакате

Методология обещает порядок в растущем фронтенде: семь слоёв, одно направление импорта, явный публичный API у каждого слайса. Здесь — «идеальная картинка», ради которой и пишется FSD.

Слои

Импорт только сверху вниз. Нижние слои ничего не знают про верхние.
app
Композиция, провайдеры, роутер, инициализация. Единственное место, где слои встречаются друг с другом.

база

Цвет верхнего слоя (app) подчёркивает его исключительность: он — единственная «корневая» директория, остальные слои живут без знания о приложении в целом.

Анатомия слайса

Любой слайс — это публичный API и приватные сегменты.
features/auth/auth-by-google/
  ├── ui/ # кнопки, экраны фичи
  ├── model/ # стор, схемы, селекторы
  │   ├── slices/
  │   ├── selectors/
  │   └── services/
  ├── lib/ # утилиты, хелперы
  └── index.ts # ← публичный API
ui — визуальные компоненты
model — данные и логика
lib — переиспользуемые хелперы
index.ts — единственная «дверь»

Публичный API

Контракт между слайсом и потребителями. Прямой импорт «внутрь» — запрещён.
UI
export { AuthByGoogle } from './ui/AuthByGoogle';
model
export { fetchAuthGoogle } from './model/services';
lib
export { googleSignIn } from './lib/google';

Идея: внутри слайса можно рефакторить как угодно, пока публичный API стабилен. Потребители зависят только от него.
